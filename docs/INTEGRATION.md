# Анализ и интеграция

## Исходные проекты

| Проект | Как получает данные | Ограничения |
|---|---|---|
| `yamaps_parser` | HTTP-запрос определяет границы города; Playwright открывает карты, собирает SSR и ответы `/maps/api/search`, прокручивает список. Город обходится сеткой с дроблением насыщенных ячеек. | Непубличная структура SSR/XHR, CAPTCHA, ограничение результатов одного viewport, отсутствие email в поисковой выдаче. |
| `parser-2gis-new` | Chrome DevTools / pychrome: переходы по страницам списка, клики по карточкам, перехват ответа каталога `items/byid`. | Зависит от DOM, Chromium/WebGL, структуры ответов и доступности сайта. Контакты могут отсутствовать. |
| `espocrm` | PHP SPA, REST API, реляционная БД. Лиды штатно предназначены для людей, однако есть поля компании и контактов. | Исходники не являются установленным релизом: нужны PHP-зависимости, сборка клиента и БД. Много модулей для этой задачи не используются. |

Для запуска используется готовый релиз EspoCRM 10.0.11 с custom-слоем из этого репозитория. Так не требуется собирать весь клиент и устанавливать PHP на рабочий компьютер. Исходные файлы CRM сохранены; настройки лежат в `espocrm/custom/Espo/Custom` и накладываются на официальный образ.

## Локальное рабочее пространство

CRM и панель работают без пользовательского входа. Для браузера добавлен минимальный стартовый экран, автоматически открывающий единую базу; профиль, выход, персональные уведомления, поля ответственных и групп убраны. Задачи можно сохранять без ответственного. Клиентские расширения находятся в `espocrm/client/custom` и копируются в постоянный том при старте образа.

Движку EspoCRM нужен внутренний контекст пользователя: middleware `Classes/Api/LocalWorkspace.php` использует служебные реквизиты сервера для первоначального открытия. Браузер не получает пароль, ему выдаётся обычный внутренний токен. Новая сессия открывается автоматически, поэтому состояние не зависит от сохранности cookies. Для запросов с `X-Api-Key` сохраняется обычная проверка ключа и ограниченная роль интеграции.

У панели нет Basic Auth и переменных `LEADGEN_USER`/`LEADGEN_PASSWORD`. Оба сервиса доступны через loopback-порты, проверяют Host и отклоняют запросы с чужим Origin. Сравнение Origin в CRM использует схему, хост и нормализованный порт без userinfo: PHP может включить техническую HTTP-авторизацию в URI, и сравнение полной authority ошибочно блокировало корректные браузерные записи.

Данные общие и хранятся в MariaDB/SQLite на постоянных томах. Закрытие браузера, очистка cookies, новая сессия или перезапуск сервисов не удаляют статусы, заметки, задачи, результаты и историю сбора. Существующие записи и служебные ссылки аудита не удалялись; пользовательских разделов и назначения записей в рабочем процессе нет.

## Передача данных

`leadgen.collectors` запускает существующие реализации, а не дублирует их логику работы с картами. Обработчик каждой полученной компании немедленно записывает её в SQLite. Остановка CRM не останавливает сбор и не теряет компании.

`observations` хранит данные каждого источника по его ID; `companies` — объединённую карточку и ревизии отправки. `job_records` связывает уже сохранённые компании с заданием для продолжения. После сбоя обновление отправляется с той же величиной `cLeadgenId`. У поля в CRM есть уникальный индекс; перед созданием выполняется поиск по нему. При потере ответа на POST следующая синхронизация находит уже созданный лид.

Проверка на установленной EspoCRM выявила два существенных отличия от первоначального тестового транспорта. JSON-фильтр поиска нужно передавать в `searchParams`: строковый `where` сервер игнорирует. Клиент дополнительно сверяет ключ каждой найденной записи и останавливает импорт при неоднозначном результате. Поля интеграции используют `clientReadOnly`, чтобы интерфейс не предлагал их редактирование, а REST API принимал значения; серверный `readOnly` отбрасывал их при сохранении.

POST автоматически не повторяется внутри HTTP-клиента. GET и PUT повторяются при временных сетевых ошибках и HTTP 429/502/503/504 с паузой; числовой `Retry-After` учитывается. Ошибки доступа или валидации сохраняются в очереди. Проверка стандартных дублей EspoCRM по имени/email для интеграции пропускается: она мешала бы сохранять разные филиалы с общими контактами; вместо неё используются локальное сопоставление филиала и уникальный ключ интеграции.

Ошибки HTTP 400/409/422 при POST/PUT относятся к конкретной записи: она остаётся неотправленной, пакет продолжает обрабатывать остальные компании. Ошибки GET, доступа, сети и сервера останавливают пакет, чтобы при общем отказе не повторять одинаковые запросы для всей очереди. Это проверено контрактными тестами. Успешные сценарии импорта на установленной CRM проверены отдельно скриптом `scripts/check_crm.py`.

Менеджерские поля импорт не изменяет. Контактные массивы дополняются с сохранением существующих флагов opt-out. Компания, найденная одновременно на двух картах, сохраняет обе ссылки. Связка рассчитана на один экземпляр сервиса очереди; SQLite и файлы checkpoint не предназначены для нескольких параллельных реплик.

Healthcheck использует штатную команду `bin/command config:get isInstalled`. Прямое чтение `data/config.php` не подходит для EspoCRM 10: признак установки хранится в `config-internal.php`, и зависимые сервисы не запускались, хотя установка уже завершилась. Результаты запуска и проверок: [TESTING.md](TESTING.md).

## Исправления парсеров

* Яндекс: результаты родительской ячейки сохраняются до дробления. Раньше они отбрасывались, и ошибка дочерней ячейки могла потерять уже найденные компании.
* Яндекс: атомарный JSON checkpoint хранит собранные карточки и завершённые ячейки; повреждение подписи поиска обнаруживается. После ограничения доступа промежуточный результат сохраняется.
* Яндекс: лимит отдельной ячейки не расходуется на дубли из соседних ячеек; ограничение результата применяется к общей выборке.
* Яндекс: проверяются bbox, нулевые размеры ячеек и отрицательные лимиты, исключающие зависание обхода.
* Яндекс: HTTP 403/429 и признаки CAPTCHA вызывают остановку, а не успешный пустой результат. Сетевые ошибки ячеек повторяются с растущей паузой и небольшим случайным смещением.
* Яндекс: браузер использует свой User-Agent вместо фиксированной устаревающей версии Chrome. Ссылки сохраняют полезные query-параметры; удаляются метки аналитики. Получаются все ссылки сайтов, а не только первая.
* 2ГИС: HTTP 4xx/5xx больше не считаются успешным получением карточки; ошибки JSON и API-коды проверяются отдельно.
* 2ГИС: таймауты повторяются с паузой, а HTTP 403/429 останавливают сбор. Задержка между кликами по умолчанию — 1500 мс; в общей панели минимум 1 секунда.
* 2ГИС: ожидание XHR не зависает на отсутствующем счётчике; присутствие старой ссылки не отбрасывает все новые ссылки страницы.
* 2ГИС: продолжение задания пропускает уже сохранённые ID. Общая интеграция извлекает все телефоны и email, а не только первый контакт каждого типа, как прежнее карточное представление.

## Ограничения и блокировки

Рабочая стратегия — уменьшить лишние обращения: один последовательный сбор, разумный лимит, паузы между действиями, сохранённый прогресс и пропуск готовых карточек. На временные ошибки используются повторы с увеличением пауз. CAPTCHA или отказ в доступе останавливают задание; пользователь восстанавливает доступ в обычном браузере и продолжает позже. Автоматического решения CAPTCHA или гарантии обхода блокировок здесь нет. Новый контейнерный браузер может иметь другую сессию, поэтому ручная проверка в отдельном браузере сама по себе не гарантирует снятия ограничения с контейнера.

Разбиение Яндекса на районы помогает уменьшить обрезание поисковой выдачи, но увеличивает число запросов и не гарантирует полноту базы. На больших городах начинайте с небольшого лимита, проверяйте качество компаний и увеличивайте паузу при ограничениях.

Для регулярных объёмных сборов более устойчивый следующий вариант — официальные API с собственными ключами. У [Яндекса есть API Поиска по организациям](https://yandex.ru/maps-api/products/geosearch-api), у [2ГИС — Places API](https://docs.2gis.com/api/search/places/overview). Доступность контактов и право хранения результатов зависят от выбранного продукта и договора. Адаптеры официальных API в эту версию не входят; ключи и тарифы не подключались.

Условия 2ГИС требуют отдельного выбора продукта: API-подписка сама по себе не подтверждает право создавать постоянную клиентскую базу. Для этого сценария рассмотрены также Дата.2ГИС и отдельные выгрузки динамики организаций. Подробное исследование первоисточников и отличия от текущего парсера: [2GIS-RESEARCH.md](2GIS-RESEARCH.md).

Сбор email с сайтов в исходном Яндекс-парсере остаётся опцией `--emails`. В общей панели он не включён: это отдельные запросы к сторонним сайтам и заметное увеличение времени. Можно обогатить CSV исходным скриптом и импортировать её в общую очередь.
